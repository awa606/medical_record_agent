# 病历历史版本查看：增量设计评审

## 输入与边界

用户要求医生修改病历后能够查看原有版本，实施授权来自本轮请求。代码基线 `5faa8b6`，当前应用 `ab8b0c5a`。复用已通过的 `20260922_alpha42_evidence_revision.md` 版本契约。

Research：本次不适用新技术选型。现有接口、SQLite完整快照、原生JavaScript与详情抽屉均复用；不引入库、不新建接口或存储，不需要以外部研究替代内部机制验证。

ASSUMPTION A01：用户需要查看旧版而非恢复覆盖。本轮先交付只读功能，文案明确“不会替换当前病历”；恢复属于后续独立写操作。

## 实现约束

- 入口在病历当前版本附近，只有已保存任务时显示。
- 默认展示最近一个旧版本；版本列表显示版本序号、保存时间、来源中文、当前标记。未知来源保留原码并说明。
- 历史字段取各自 `fields_json`，必要时仅回退该版本 `result_json.fields`；无法解析则说明，不从当前内容补造旧版。
- 原文引用随对应历史版本展示；候选诊断/处理建议以该版本快照为准。仅比较已保存内容，当前未保存文字保留且不参与对照。
- 候选与当前差异使用字段级原值对照，不引入字词diff算法。所有数据库文字转义。
- currentRevisionInfo只在id匹配时回退到本就诊revision_no，不再把全局主键显示成“版本号”。

## 固定五问与结论

1. 为什么这样拆：保存/授权已有事实源，只补医生入口，避免重写版本管理。
2. 替代方案：直接数据查看器对医生操作成本高；新增历史API、恢复写入或diff库本轮没有必要。
3. 最大失败点：异步返回污染当前编辑及版本身份混淆，必须独立状态与上下文核验。
4. 最小验证：现有16项回归，加前端旧版显示/编辑不变/竞态及后端GET只读与权限用例。
5. 完成证据：通过可见按钮查看本就诊v1与后续版本；截图、接口只读指纹、测试及精确部署版本分别记录。

**Design Review Gate：PASS（局部显示能力）**。不是实现测试PASS，也不是5.1或医生稳定试用放行。
