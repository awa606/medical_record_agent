# 单一活动环境与就绪刷新：研究及增量设计评审

## 事实、研究问题与决策

基线39f36b7，部署应用02af90b。本轮缓存时间Spike复现：245秒仍就绪但不刷新；301秒首次触发预热且拒绝生成。新增失败回归保留在本地证据目录。两版启动器实际拒绝PEER_RUNNING，待用户保存退出后按原切换入口恢复8798，未绕过闲置确认。

研究问题：能否复用现有成功缓存和探测，在不延长300秒有效期、不放宽模型检查的前提下消除周期性断档？选择ADAPT现有Python线程/Condition及Docker重启策略；不增加守护程序、框架或数据库。

候选比较：延长TTL不能证明模型持续可用；页面定时请求依赖浏览器常驻；应用生命周期内刷新不依赖页面且复用现有检查。最大风险是探测与生成竞争，因此使用每模型的单一推理槽：业务等待者优先，探测遇忙直接延后。已开始的HTTP推理不强行中断；不能承诺抢占正在执行的探测。针对缓存期限的必要Spike已执行，运行机制Research PASS；候选模型质量仍NEEDS MORE EVIDENCE。

官方依据：[Docker重启策略](https://docs.docker.com/engine/containers/start-containers-automatically/)。仅活动版显式选择unless-stopped，闲置版始终no；手动停止不自动恢复。不创建系统计划任务。

## 增量设计

| 评审项 | 本批边界与验证 |
| --- | --- |
| 目标、交付物 | 8798重复启动、受控异常恢复；20分钟就绪连续采样；原知识/病历保留 |
| 输入输出 | 启动器注册配置/容器状态→已验证环境；模型摘要/成功时刻→原有ready响应 |

| PBS、架构 | 原启动器＋原Ollama Provider＋readiness生命周期监控；不新增公共API |
| 模块与数据 | 启动器拥有容器策略；readiness拥有进程内成功缓存、在途探测及推理槽；Provider拥有实际HTTP请求 |

| 风险 | 刷新与业务竞争、探测失败、模型失联、两个环境误启动；分别以槽、失效、摘要/驻留核验、peer注册校验阻断 |
| 最小验证与验收 | 假时钟/并发事件回归覆盖到期、失败、摘要变更；实际冷启动、重复启动、异常应用退出、20分钟采样 |
| 回退 | 保留02af90b镜像及SQLite一致性备份；恢复原注册与策略；不删除旧数据 |

ASSUMPTION A01：生产仅一个应用进程管理该Ollama实例；其他应用进程/外部Ollama调用不受本进程推理槽控制。当前部署核验后适用。

为什么这样拆：启动策略与推理新鲜度有不同状态所有者，可以独立回归和回退。替代方案及风险见上；最可能失败的是资源竞争，通过事件回归和真实运行验证；完成需实际20分钟与恢复记录，不能只凭测试文件。
