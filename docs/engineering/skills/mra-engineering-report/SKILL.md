# MRA 工程迭代汇报

先完成已授权的工作，再报告实际结果。此 Skill 只约束本项目的沟通与证据表达，不代替 PM、Research、Design 或安全推送规则，不授予采购、训练、合并或改动范围的额外权限。

## 选择汇报方式

- 完整迭代总结、阶段汇报及用户明确要求的完整说明，采用现有 [project-progress-report-cn](C:/Users/AWA007/.codex/skills/project-progress-report-cn/SKILL.md) 的十一问。实际读取其问题解释与证据要求；下列题目供项目内读者识别结构，不另复制一套详细规则。
- 十一项写在聊天最终答复正文中，附件和链接作为补充；不同时再输出旧六项结构。
- 日常小步进展围绕“发现了什么、影响什么、下一步验证什么”组织；具体追问先把问题解释完整，不为填满十一项重复历史。
- 用户当次明确指定的格式优先。计划、只读或前置受阻时，分清本轮实际核查与最近工程交付，未实施的动作不能写成完成。

## 完整汇报十一问

1. **目前到什么阶段？**
2. **完成了哪些功能？**
3. **还有什么功能没完成？**
4. **目前的问题是什么？**
5. **这一轮的交付输出是什么？**
6. **你的解决方案有哪些？**
7. **搜索到的开源的或成熟的解决方案有哪些？**
8. **你的解决问题的思路是什么？**
9. **你的下一步建议是什么？**
10. **为什么下一步要这么干？**
11. **下一轮的交付输出是什么？**

## 把当前问题解释清楚

关键问题按实际操作讲清：用户想做什么、预期与实际有什么不同、属于哪类问题及已定位到哪一层、影响哪些操作与可用退路、哪些证据已确认而原因仍未知、当前处理状态和下一项验证。用连贯段落或必要的对照表表达，不再为此增加另一套固定标题。

关键阻断、失败方案和被拒候选应充分解释，不把每项一两句话当长度目标。先说软件怎样响应和用户怎样继续，再解释技术名词；版本号、模块名和测试总数只用于支撑判断。唯一下一任务应说明优先理由和停止条件；需要用户帮助时只列真正缺失的输入或操作，不重复征求已有授权。

## 本项目必须保留的区别

- 当前运行前端、运行后端与文档提交分别标注；服务可访问、历史验收通过及本轮新验收是不同事实。Planner注明实际采样时间，历史文件哈希一致不能写成实时快照。
- 模型首次输出、规则拦截、医生修改后结果分别统计。规则测试通过率不得写成模型准确率。
- 界面基线、模型候选与完整可恢复发布是不同交付。真实三路径及对应SHA恢复证据缺失时，不宣布稳定发布。
- 合成、历史回放、复用真实录音、本轮物理麦克风各自标识。假录音测试不替代物理证据。
- 知识指南是医生参考，不能自动变为患者事实；缺失、冲突、失败不可用固定文本／Mock／云端回退掩盖。
- 不承诺“所有病历均正确”。报告支持范围、具体失败和可拒绝路径。
- 按输入→ASR→角色→理解→校验→工作流→训练定位相关层，一次改变一个可验证因素；诊断进展不能冒充产品效果已改善。
- 失败交付保留“模块／输入ID／预期与实际／影响／证据位置／下一最小验证”。无新增搜索或实验时如实写明，不为栏目凑方案或重复测试。

## 复核与同步

- 按项目既有三角色职责实际复核受影响功能，区分实现者自测与独立检查。实际截图、接口测试、录音、缩放及用户认可分别记录，不能把Skill加载或主线程自查改名为独立复核。
- 已通过且未受影响的证据注明版本、时间与适用范围后复用；只补变化、新失败与缺失项。没有新截图时明确视觉证据限制，不为报告重新设计页面。
- 遵循既有PM收尾：验证同轮快照→同步Obsidian→提交实质交付取得SHA→导出状态镜像→提交镜像→推送→更新PR。镜像repo_sha不指向镜像提交；纯只读或无事实变化不制造提交。

每项先给结论，再提供足够依据。简洁是省去无关内容，不省去用户理解当前问题、影响和下一步所需的信息。
