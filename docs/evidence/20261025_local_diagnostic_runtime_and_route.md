## 2. 逐层定位及最小处理

### 2.1 本地实验：先确认运行时，再看资源

第一轮固定协议登记Ollama `0.40.9`，实际二进制及服务返回 `0.40.10`。协议按设计停止，没有预热或调用模型，不把跨运行时结果混为同一对照。原协议SHA256为 `24621192882b7b0f4c5919b09f0654acd2bbbb3ab1569f9a97c3d16528435fd1`。

第二轮新建独立 `0.40.10` 协议，计划先重建同运行时原版数组基线；只有基线失败才进入最多三次自由布尔选择。字段不得强制true，原句ID、目录事实、主体及原采样参数不变。协议SHA256为 `6a44698380a2c4f63241acbb7381e05a277e921024b898a9c38426051e1798f9`。

用户已保存退出，且授权暂时停止旧2666。两套项目服务暂停后的资源检查记录：

- Windows可用内存 `5,017,128,960` 字节，约4.67GiB，低于既有8GiB启动线。
- 显存可用5549MiB，通过4500MiB前提，但不能抵消内存失败。
- `RESOURCE_PREFLIGHT_FAILED`；零预热、零病例调用，未下载模型，未降低门槛，未关闭无关应用或重启WSL。

停止容器不保证内存立即回到Windows。Docker官方说明WSL页缓存可能持有内存，并建议结合WSL的自动回收机制。本轮未证明页缓存就是缺口全部来源，未修改全局WSL设置。下一次诊断先取得资源确实回收的采样，再复用该固定协议；不重复执行同样的立即启动失败。

### 2.2 恢复阶段：本轮辅助备份脚本未及时关闭连接

第一轮辅助脚本使用SQLite连接上下文管理器备份后，在同一进程内启动Linux容器，但没有显式关闭宿主机数据库连接。恢复时出现WAL相关磁盘I/O错误。结束该辅助进程、释放连接后，同库能正常启动，`quick_check=ok`。第二轮改为容器内SQLite Backup API，并用 `contextlib.closing` 明确关闭源、目标连接。

这是本轮新辅助脚本的缺陷，不是已经确认的产品数据库损坏。没有删除WAL/SHM，没有覆盖原库，也不能用它解释当天11:05原容器退出的原因；原退出原因仍未确认。

### 2.3 在线生成：显式代理端口失效

原8798配置指向 `http://host.docker.internal:7890`，但宿主机7890没有监听。宿主机和容器的直接HTTPS访问可达；相同既有密钥的模型可用性检查通过，未调用生成接口。故障在网络路由层。

修复仅将 `ONLINE_LLM_PROXY_URL` 显式设为空字符串，表示直连。不是失败时自动切换路由。新容器先创建但不运行，检查镜像、环境、挂载及网络后，停止旧容器并启动已检查的新容器：

- 应用环境唯一变化是该代理变量；网关环境没有变化。
- 镜像、挂载源及读写权限、命令、用户、端口、数据库目录和页面资源一致。
- 复用原Docker网络，核对网络ID与 `Internal` 属性不变；内部网络仍隔离。
- 旧应用和网关停止保留，新应用和网关运行；旧2666已恢复健康。
- 切换回执健康200、就绪200，切换本身费用账本未变。
