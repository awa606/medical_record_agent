# R-1.2 Alpha 目标运行环境

## Problem

确认 `MRA-ALPHA-ENV-01 Rev.2` 是否值得进入 Jetson Orin Nano Super 8GB 实机验证。开发机只能作为 `MRA-ALPHA-DEV-01`；x86、独立显存和 Docker Desktop 结果不能证明 Jetson ARM64/CUDA 与 8GB 共享内存通过。

## Research Questions

1. JetPack 6.2.3 与 7.2.1 中，哪个版本的 Docker、CUDA、PyTorch 与 Ollama 组合更适合首轮 Orin 实机验证？
2. 现有 FunASR upload profile 应直接复用、改走 ARM64/ONNX CPU，还是适配 Jetson PyTorch/CUDA 容器？
3. Qwen3:4b 与 FunASR 在 6.5 GiB 服务预算内串行执行是否能产生有效输出并可靠释放资源？
4. 开发套件、512GB NVMe、外壳、USB会议麦克风、网线和安装介质的含税运费总价能否不超过3000元？

## Existing Internal Solution

- `FunASREngine` 在 FastAPI 进程内持有四个 upload profile 组件，不会在一次转写后自动退出。
- `OllamaLLMProvider` 当前固定使用 `num_ctx=8192`、`num_predict=2048` 和 `keep_alive=30m`。
- 开发机已有真实 FunASR、Qwen3:4b、Docker 与本地闭环证据；Jetson 尚未到货。
- 历史 streaming 五组件出现过 OOM；稳定证据来自 upload 四组件。
- Qwen3:4b 本地缓存摘要为 `359d7dd4bcdab3d86b87d73ac27966f4dbb9f5efdfcc75d34a8764a09474fae7`，模型文件约2.5GB。

## Decision-Critical Unknowns

- **U01（开发机已回答）**：FunASR/FastAPI在6.5 GiB内完成启动及三段音频转写，但峰值约6.17 GiB、余量很小。
- **U02（开发机已回答为否）**：Qwen3:4b及1.7B在当前CPU共享内存估算下均未于300秒内返回合法Schema。
- **U03（部分回答）**：进程隔离后的两个LLM候选均能在约1秒内卸载；ASR通过终止独立进程释放，但Jetson上的重新加载成本尚未验证。
- **U04**：Jetson ARM64/CUDA的软件栈与实机性能。
- **U05**：完整BOM的两份含税运费报价及复用小件替代价值。

## Spike

实验脚本为 [`scripts/run_target_resource_spike.py`](../../scripts/run_target_resource_spike.py)，原始输出保存于本地 `.artifacts/target-env-spike-20260914/`。服务预算不超过6.5 GiB，`memory-swap`与`memory`相同，不启用额外swap。

### Phase A：当前常驻对照

- FastAPI/FunASR：4864 MiB。
- Ollama：1792 MiB。
- 结果：FunASR预热阶段被OOM杀死，Exit 137；LLM尚未加载。

### Phase B：进程隔离串行

- FastAPI/FunASR独占6656 MiB。
- 四个upload组件在84.9秒后ready。
- 三段音频成功3/3；处理时长44.930、71.856、16.486秒，最大RTF 0.1514。
- cgroup峰值6,629,724,160字节（约6.17 GiB），swap为0，OOM为0。
- 这是开发机资源筛选PASS，不代表Jetson的系统、ARM/CUDA、温度或持续运行通过。

### Phase C：资源优化LLM Smoke

- Ollama限制5888 MiB，执行器限制640 MiB；CPU-only，`num_ctx=2048`、`num_predict=512`、`keep_alive=0`。
- Ollama峰值约2.903 GiB，无swap、无OOM。
- 1个合成病例在300秒超时，合法Schema为0/1；超时后模型约1秒卸载。
- 该结果只说明4B权重可装入当前CPU容器预算，不能证明有效输出、性能或Jetson兼容。

### Phase C2：Qwen3 1.7B停止条件复测

- 官方`qwen3:1.7b` Q4_K_M模型，摘要前缀`8f68893c685c`，约1.4GB。
- 与4B相同的5888 MiB Ollama、640 MiB执行器、`num_ctx=2048`、`num_predict=512`、`keep_alive=0`和CPU-only条件。
- Ollama cgroup峰值1,921,376,256字节，无swap、无OOM；单例300.110秒超时，合法Schema为0/1；模型0.912秒内卸载。
- 依照停止条件不再扩展到10例。1.7B降低了内存占用，但没有解决当前开发机CPU时延和有效结构化输出问题，不能作为4B替代版本。

完整摘要见[资源Spike检查点](../evt/evidence/20260914/alpha12_target_resource_spike/README.md)。

## BOM价格边界

2026-09-15可核实的公开价格相互冲突：NVIDIA中国产品页仍显示人民币2070元，NVIDIA当前FAQ显示开发套件MSRP为399美元；京东页面显示3699元，Waveshare页面显示544.99美元。京东单套价格已经超过3000元，而其他页面不能证明送达当前地址后的含税运费总价。因此完整BOM尚无两份可比的含税运费报价，预算Gate继续为`MORE_EVIDENCE_REQUIRED`。

## 固定七问

1. **别人是否已经解决过？** NVIDIA、Ollama和FunASR已有可复用软件栈与runtime，但没有证据证明本项目组合在8GB Orin上通过。
2. **能否直接复用？** 当前证据不足；x86镜像不能直接作为Jetson镜像，1.7B也未通过结构化输出停止条件。
3. **复用最大风险？** FunASR常驻内存、ARM64依赖、CUDA容器兼容和4B结构化生成时延。
4. **最小成本验证？** 先完成本开发机6.5 GiB串行Spike，再借用或采购Jetson做分层实机验证。
5. **证据是什么？** cgroup内存、OOM/Exit状态、模型摘要、Schema校验、三音频指标和完整BOM报价。
6. **为什么选择REUSE/ADAPT/BUILD？** 尚未选择；开发机Spike已经完成，但Jetson兼容、实机性能及完整BOM仍缺决策证据。
7. **判断错误如何回退？** 保留Rev.1历史证据；拒绝Jetson候选或改用1.7B/ONNX路线，不影响已合并的PR #100。
