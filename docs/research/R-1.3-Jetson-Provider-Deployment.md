# R-1.3 Jetson Provider 部署研究

## Problem

冻结 Jetson Orin Nano Super 8GB 上的 ASR、LLM、容器、缓存和就绪语义，使设备到手后可以直接开始两小时 Bring-up Smoke。本记录不证明 Jetson 已通过，也不授权修改生产 Provider。

## Constraints

- 目标设备：`MRA-ALPHA-ENV-01 Rev.2`，8GB 统一内存。
- 必须离线运行，禁止 Mock、云端 Provider 和未披露 fallback。
- 复用现有 API、字段证据、安全门禁和本地模型缓存。
- 开发机资源 Spike 已证明 ASR/LLM 共驻留会 OOM；必须串行管理生命周期。
- 本轮只完成 Research、部署矩阵、Runbook 和验收入口。

## Existing Internal Solution

| 资产 | 已证明 | 不能外推 |
|---|---|---|
| `FunASREngine` upload profile | x86 CPU 可加载 Paraformer、VAD、标点和 CAM++，三段音频完成 | ARM64、CUDA、Jetson时延和温度 |
| `OllamaLLMProvider` | `qwen3:4b`真实结构化输出及模型摘要追踪 | 8GB Jetson 性能 |
| 资源 Spike | 共驻留 OOM；隔离 ASR 可运行；LLM可卸载 | Jetson统一内存和GPU行为 |
| `/health`、`/ready` | 开发机能核验存储和真实Provider | 当前预热逻辑与严格串行生命周期不兼容 |
| `compose.local-loop.yml` | 开发机闭环配置可复现 | `python:3.11-slim`及CPU PyTorch不是Jetson GPU基线 |

## Decision-Critical Unknowns

- **U01**：`25.06-py3-igpu`中安装`funasr==1.3.29`及现有模型依赖是否无冲突。
- **U02**：FunASR CUDA与CPU在真实Orin上的时延、峰值统一内存和温度。
- **U03**：固定摘要的Qwen3:4b在`num_ctx=2048`下能否及时返回合法Schema。
- **U04**：当前FastAPI就绪探测如何与ASR/LLM非共驻留状态机结合。

这些问题必须由真实设备或后续Design Review解决；继续使用x86模拟不能消除它们。

## Deployment Decision

**Decision：ADAPT**

复用现有FunASR模型链、Ollama接口、Schema、安全门禁、缓存事实和就绪语义；新增Jetson专用运行锁定与串行生命周期适配。直接复用被拒绝，因为当前镜像、Python/PyTorch和预热策略属于x86开发基线。自研被拒绝，因为NVIDIA、FunASR与Ollama已有足够的官方运行基础。

### Preferred Stack

| Layer | Frozen value |
|---|---|
| Board | Jetson Orin Nano Super 8GB |
| Host | JetPack 6.2.3 / L4T 36.5.2 / Ubuntu 22.04 |
| Host Python | 3.10，仅用于系统工具和验收脚本 |
| Container runtime | Docker Engine + NVIDIA Container Toolkit |
| ASR base | `nvcr.io/nvidia/pytorch:25.06-py3-igpu`，首次拉取后记录ARM64 manifest digest |
| ASR Python | 镜像自带Python 3.12；`funasr==1.3.29`，先做依赖安装Smoke |
| ASR profile | upload四组件；streaming五组件不在本轮范围 |
| Ollama | `ollama/ollama:0.34.0@sha256:684d8674b4315fa18f4f0e973a118ec2652ed96f67563277839985175858e0ba`，`JETSON_JETPACK=6` |
| LLM | `qwen3:4b@359d7dd4bcdab3d86b87d73ac27966f4dbb9f5efdfcc75d34a8764a09474fae7` |
| Generation | `num_ctx=2048`、`num_predict=512`、`think=false`、`keep_alive=0`、并行度1 |

### Fallback Stack

FunASR首选路线在依赖安装、启动或内存阶段失败时，切换到官方ARM64 ONNX CPU Runtime 0.4.6做独立转写Smoke。该路线只能证明引擎可运行；接入现有`ASRResult`、分段与角色链路前必须另做Design Review。Qwen3:4b失败时只启动1.7B资源筛选，冻结病例41–60的结构和安全回归通过前不能替代4B。

## Memory and Cache Strategy

1. FastAPI保持轻量运行；ASR容器独占模型阶段。
2. ASR结果和证据写入SQLite/运行目录后停止ASR容器，确认进程消失与内存释放。
3. 再启动Ollama并加载Qwen3:4b；生成后发送`keep_alive: 0`并在30秒内确认卸载。
4. 不允许ASR预热和LLM就绪探测同时使两组模型驻留。
5. NVMe目录固定为`/srv/mra-alpha/model-cache/{modelscope,hf,torch,ollama}`；模型、镜像与配置生成SHA256清单，权重不进Git。
6. 部署后NVMe可用空间必须不少于100GB。

## Health and Readiness

- `/health`：进程存活即可返回200，不代表模型、存储或业务闭环就绪。
- `/ready`：只有SQLite与运行目录可写、指定ASR完成真实探测、固定摘要LLM完成有效推理、无Mock/云回退且生命周期状态一致时返回200。
- 两小时分层Smoke期间，在ASR和LLM尚未完成联合编排前，`/ready`返回503是预期结果，不得伪装PASS。

## Evidence and Rollback

- Runbook：[`docs/engineering/alpha13_jetson_provider_bringup.md`](../engineering/alpha13_jetson_provider_bringup.md)
- 验收入口：[`scripts/validate_alpha13_jetson_smoke.py`](../../scripts/validate_alpha13_jetson_smoke.py)
- 回退顺序：停止当前阶段容器 → 保留日志与运行目录 → 恢复已验证镜像/模型摘要 → 仅重试失败层。不得同时更换JetPack、基础镜像、ASR和LLM。

## Fixed Seven Questions

1. **别人是否已经解决过？** NVIDIA提供Jetson软件栈和iGPU容器，FunASR提供ARM64 Runtime，Ollama提供JetPack容器入口。
2. **能否直接复用？** 不能；现有生产镜像和预热语义针对x86及共驻留，需要有限适配。
3. **复用最大风险？** Python/FunASR依赖、统一内存、模型时延及顺序就绪状态。
4. **最小成本怎么验证？** 借用8GB Jetson，按Runbook先跑两小时分层Smoke。
5. **证据是什么？** 官方版本矩阵、现有资源Spike、模型摘要和实机验收JSON。
6. **为什么选择ADAPT？** 核心引擎和业务接口已存在，差距集中在目标运行栈及生命周期管理。
7. **判断错了如何回退？** ASR退到官方ARM64 ONNX CPU Runtime；LLM仅在回归通过后筛选1.7B；保留开发机基线。

## Research Gate

**PASS**。已具备直接开始真实板卡两小时Bring-up所需的版本、候选、顺序、证据和停止条件。该PASS只关闭部署研究，不代表1.2、1.3、Jetson或Alpha验收通过。
