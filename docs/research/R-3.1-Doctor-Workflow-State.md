# R-3.1 医生工作台状态流整合

## Problem

医生工作台已经有五步界面、就诊恢复、SSE、审核和导出，但没有单一的前端状态事实。`appState.taskStatus`有时保存大写`task.status`，有时保存小写`current_stage`；就诊列表又优先使用`encounter.status`。同一个任务因此可能在工作列表显示“待录入”、主面板显示`input`，同时“下一步”显示“AI处理中”。

## Constraints

- 保持现有五步业务流程和公共HTTP接口。
- 不修改数据库、Provider、角色门禁阈值或录音/ASR实现。
- 角色确认继续作为异常恢复入口，不成为第六个常驻步骤。
- 完整修改、审核和导出验收属于WBS 3.3；跨刷新完整恢复属于Alpha+。

## Existing Internal Solution

- `static/doctor.js`已有`WORKFLOW_STEPS`、`STATUS_TO_STEP`、`doctorDisplayState`、`workflowStepKey`、`nextActionState`和`encounterPhaseLabel`。
- PR #54建立五步医生工作流；PR #65建立Encounter工作列表和草稿恢复；PR #108补齐角色质量409恢复。
- 后端已经同时返回`encounter.status`、`task.status`和`task.current_stage`，无需扩展API。

本任务没有决策关键的外部Library未知，因此停止外部搜索。引入新框架不会解决现有别名和优先级问题。

## Unknowns and Spike

### U01

同一后端任务是否会在工作列表、主状态和下一步面板产生不同状态？

### Minimal Spike

- **Input**：本地Test DB中的匿名Encounter和真实`/api/encounters`、`/api/tasks`响应。
- **Cases**：`transcribing`、`extract_fields`、`doctor_review`、`waiting_doctor_review`、`approved`、`failed`。
- **Procedure**：浏览器从真实API恢复同一Encounter，读取工作列表、`body.dataset.displayState`、步骤条和下一步标题。
- **Pass**：四处共享同一规范状态，且大写`status`与小写`current_stage`别名结果一致。
- **Stop**：出现首个不一致即证明REUSE不足。

### Result

2026-09-21在`fac6de6e`基线上执行Spike，首个`TRANSCRIBING/transcribing`样本即失败：

- 主状态：`input`
- 工作列表：无规范状态，阶段为“待录入”
- 下一步：`AI处理中`
- 测试结果：`1 failed`

这证明缺口来自状态派生，不需要更换后端或重写工作流。

## Decision

**ADAPT EXISTING DOCTOR WORKFLOW**

增加一个纯内部规范化层，将`encounter.status`、`task.status`、`current_stage`和必要的浏览器运行态派生为唯一医生端状态；现有各展示区域只消费该结果。

## Fixed Questions

1. **别人是否已经解决过？** 项目内部已实现业务流程和恢复，只缺统一状态派生。
2. **能否直接复用？** 不能原样复用；分散判断已产生真实不一致。
3. **最大风险是什么？** 统一时改变角色门禁、审核或导出的既有优先级。
4. **最低成本验证是什么？** 一份真实API驱动的浏览器状态契约测试。
5. **证据是什么？** 失败Spike、现有API响应及历史PR #54/#65/#108。
6. **为什么选择ADAPT？** 能保留所有公共契约，只修改UI边界的状态解释。
7. **判断错误怎样回退？** 回退单一状态规范化提交，恢复原分散映射；后端数据不需迁移。

## Implementation Verification

规范化层实施后，相同的真实API表驱动用例六种状态全部通过；定向回归34项、完整pytest 515项和8个subtests通过。结果支持最初的ADAPT决策，不需要引入新的状态机或修改后端契约。详见[`20260921_alpha31_doctor_workflow_state.md`](../evidence/20260921_alpha31_doctor_workflow_state.md)。
