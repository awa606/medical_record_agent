# R-4.2 字段证据、知识引用与 Revision 关联研究决策

## Problem

WBS 4.2 要证明医生修改病历后，字段仍能回到原始转写片段，候选诊断仍保留知识引用，前后版本可比较，保存并重新加载后关联不丢失。仓库已有 Revision、批准和并发控制，因此本次研究重点是确认能否直接复用，而不是重新设计版本系统。

## Research Questions

1. 现有 `record_revision.result_json` 是否完整保存字段证据和候选诊断知识引用？
2. 医生保存新版本后，`encounter_id / task_id / revision_no` 是否连续且可追踪？
3. 旧版本并发提交、旧批准和未审核导出的门禁是否已经成立？

## Constraints

- 不增加公共 HTTP API，不修改数据库结构。
- 3.3 才实现整页编辑、主动知识查询、批准和导出完整交互。
- 4.2 只证明关联、持久化、并发保护和前后版本可重算。
- 原始音频、运行数据库和身份信息不得进入 Git。

## Existing Internal Solution

| 内部资产 | 已有能力 | 证据 |
|---|---|---|
| `record_revision` | 保存完整 `fields_json / result_json / content_hash` | `app/db/sqlite.py` |
| Review 事务 | 新建 Revision、更新 Task/Encounter、失效旧批准和写审计在同一事务内 | `apply_review_revision_transaction` |
| 乐观并发 | Revision ID 或内容哈希过期返回 409 | `StaleRecordRevisionError` 与既有测试 |
| Encounter 读取 | 返回当前 Revision 与历史 Revision 列表 | `GET /api/encounters/{id}` |
| 字段证据 | `SourceSpan`保存 segment、index、起止时间 | `app/schemas/medical_record.py` |
| 知识引用 | `CandidateDiagnosis.references`保存来源、版本、URL与审查状态 | 同上 |

## Candidates

| 候选 | 方案 | 适配 | 风险 | 结论 |
|---|---|---:|---:|---|
| A | REUSE现有完整Revision JSON与事务门禁，补关联回归测试和Evidence | 5/5 | 低 | 选择 |
| B | ADAPT数据库，拆出独立字段证据和引用关系表 | 3/5 | 中高；迁移和双写增加复杂度 | 当前不选 |
| C | BUILD事件溯源或外部审计平台 | 2/5 | 高；超出Alpha范围 | 不选 |

评分依据为仓库实现、已合并PR #64、既有事务/并发测试和本轮最小Spike。

## Decision-Critical Unknown and Spike

### U01：医生修改后证据及知识引用是否原样持久化？

- 输入：匿名合成发热任务；字段引用 `seg-patient-001`，时间 12.3–14.7 秒；候选方向引用测试指南。
- 操作：创建包含证据的基线Revision，修改现病史并保存新Revision，再通过全新数据库连接重载。
- Pass：同一Encounter/Task；Revision连续；修改字段Before/After不同；未修改字段的segment、时间和知识引用完全一致。
- 结果：PASS。Revision 2→3，segment与时间完整保留，知识引用ID完整保留。

### U02：并发和批准门禁是否需要新实现？

- 既有测试已覆盖旧Revision ID/哈希返回409、并发修改仅一个成功、修改后批准失效及未重新批准禁止导出。
- 结果：PASS，无需新数据库或公共接口。

## Decision

**REUSE EXISTING REVISION TRANSACTION AND JSON LINEAGE**。

Research Gate为 **PASS / REUSE**。新增工作仅为固化证据关联契约、匿名前后比较样例和验收证据；不改生产存储模型。

## Rejected Alternatives

- 不采用独立关系表：当前Alpha字段与引用随完整Revision快照保存，能满足可追踪和恢复；拆表没有决策关键收益。
- 不采用事件溯源平台：现有审计日志、Revision和批准关系已覆盖当前门禁，企业级不可抵赖审计属于后续支线。
- 不在4.2增加前端整页Diff：整页编辑和交互属于3.3，4.2只提供可重算版本数据。

## Implementation Boundary

- 增加版本关联回归测试和匿名Before/After Evidence。
- 复用现有Revision、Review事务、Encounter读取、批准失效和409冲突。
- 不增加API、表、依赖、UI或新的状态机。

## Fixed Questions

1. **别人是否已经解决过？** 项目内部PR #64已实现当前所需的Revision事务和并发门禁。
2. **能否直接复用？** 可以；本轮Spike证明完整JSON快照保留字段证据和知识引用。
3. **最大风险是什么？** 后续整页编辑若错误重建字段对象，可能在客户端丢失只读证据；3.3必须回归本契约。
4. **最低成本验证是什么？** 一个匿名任务的两版保存、重载和逐字段关联比较。
5. **证据是什么？** 可重跑测试、Revision ID/哈希、segment/time/reference Before/After断言。
6. **为什么选择REUSE？** 现有实现满足全部4.2验收，新增数据库结构只会扩大迁移和双写风险。
7. **判断错误如何回退？** 保留完整Revision JSON；若3.3发现查询性能或独立审计不足，再以兼容派生索引适配，不破坏已有快照。

## Research Gate

**PASS / REUSE**。这只证明Alpha版本关联能力，不表示3.3整页编辑或企业级审计已经通过。
