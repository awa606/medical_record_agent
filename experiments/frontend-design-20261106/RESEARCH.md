## 问题和已知资产

此前三张设计图只能说明构图，不能验证采集、核对、恢复和返回之间的衔接。11月5日原型已有两个合成病例、四字段、版本与签署、保稿、导出模型和30项状态测试；新样机直接复用这些状态契约，并把新增采集状态限制在独立模块。

本轮比较的交付方式：

| 候选 | 适配情况 | 本轮处理 |
| --- | --- | --- |
| 继续输出图片或热点跳转 | 能比较视觉，但不足以验证患者隔离、实际输入与异常恢复 | 保留为视觉基线 |
| 在既有原型中实现确定性状态和真实按钮 | 可以无新增依赖地走完整合成流程，易回退和逐项复核 | 用作本轮研究实验 |
| 接入生产接口或更换框架 | 增加接口、存储与真实数据风险，无法由当前设计图确认收益 | 不进入本轮范围 |

这不是生产架构选型结论；生产 `reuse_decision` 仍不填写。

## 待验证问题

- U01：原文、病历与辅助提示同步变化，是否仍保持稳定阅读空间和一个阶段主动作？
- U02：手改、断连、刷新、患者切换与正式草稿交接是否保护合成内容，明确未提交状态？
- U03：用户是否认为新版足够简洁直观，目标医生在同条件任务中是否减少往返？

## 实验约定

- 假设：相同连续病历框架可以承接采集中和核对中状态，避免录音页与病历页相互割裂；交互状态可以在不访问生产系统的条件下验证。
- 输入：固定 `syn-001`、`syn-002` 合成病例，各六句对话；四字段和四类审核项。
- 环境：本机 Python 静态服务器、原生 ES Modules、Node 状态测试、内置浏览器。
- 步骤：开始接诊 → 模拟采集 → 身份确认 → 暂停/继续 → 编辑/新句 → 结束采集 → 核对/保存 → 签署 → TXT导出 → 完成/返回；另验 A/B 隔离、恢复、断连与失败。
- 观察：实际按钮结果、字段内容与版本、可见保存状态、焦点和模态返回、视口溢出。点击计数仅作原型记录，不充当医生效率结果。
- 通过条件：合成主线可操作，未提交内容不会静默跨患者或被覆盖，签署与当前版本一致；实际渲染无阻断使用的问题。
- 停止条件：工具政策拒绝、不可辨认患者归属、旧签署可导出新内容、手改丢失。停止对应检查并保存失败事实，修复后定向复验。

## 固定七问

1. **已有解决方案吗？** 有：本仓库11月5日原型及前期研究的真实产品交互模式。
2. **能直接复用吗？** 已有版本、审核、签署和草稿恢复模型可作为实验基座；采集中衔接需要实测。
3. **最大风险是什么？** 新增临时采集与正式病历双状态发生串用、手改被覆盖或把模拟结果当成临床能力。
4. **最小验证方式是什么？** 独立目录、固定两例、可暂停的逐句输入、状态测试加实际按钮检查。
5. **证据在哪里？** 本目录报告与本机 `.artifacts/frontend-prototype-20261106`；旧失败证据保留在11月5日审查目录。
6. **最终选择为何？** 本轮只确定研究实验路径；生产 REUSE/ADAPT/BUILD 尚未放行，关键用户证据仍缺。
7. **如何回退？** 停止23711原型服务并使用相邻11月5日原型；生产资源未被替换，旧文件未删除。
